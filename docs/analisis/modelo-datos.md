## 2. Traducción MySQL 8 → PostgreSQL 16 (lo que cambió y por qué)

| Legacy (MySQL) | Ahora (PostgreSQL 16) | Por qué |
|---|---|---|
| `INT UNSIGNED AUTO_INCREMENT` | `integer GENERATED BY DEFAULT AS IDENTITY` | Es el estándar SQL moderno. `BY DEFAULT` (no `ALWAYS`) para poder cargar los ids del seed y de cualquier migración de datos |
| `TINYINT(1)` 1/0 (usuarios/estudiantes/cursos) | `boolean` | Semántica real. **Impacto en la API:** el JSON pasa de `1`/`0` a `true`/`false` |
| `VARCHAR(10)` para `periodo` | `varchar(7)` + CHECK `AAAA-MM` | El legacy validaba el formato en PHP (`preg_match('/^\d{4}-\d{2}$/')`) pero guardaba hasta 10 caracteres. Ahora el mes imposible (`2026-13`) tampoco entra |
| `TINYINT UNSIGNED` para `creditos` | `smallint` + CHECK `1..10` | El rango 1..10 lo validaba `cursos/create.php`; la columna aceptaba hasta 255 |
| `estado VARCHAR(15)` de matrículas | `varchar(15)` + CHECK `activa\|retirado` | El legacy lo validaba con `in_array()` en PHP (`matriculas/create.php`) |
| `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` | `timestamptz DEFAULT now()` | Mismo instante, pero con zona: el legacy guardaba hora local sin zona. La API responde en `America/Lima` |
| `ENGINE=InnoDB`, `CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` | no aplica | PostgreSQL solo tiene UTF-8. **Ojo:** la collation `_ci` era insensible a mayúsculas **y a tildes** en los `LIKE`; PostgreSQL no lo es (ver §6) |
| `INDEX idx_estudiantes_apellidos (apellidos)` | idéntico | — |
| Índices implícitos de las FK | declarados a mano | PostgreSQL no los crea |
| `COMMENT '...'` en columnas | `COMMENT ON COLUMN` | Mismo dato, otra sintaxis (lo lee la API y pgAdmin) |
| `CREATE OR REPLACE VIEW` con `CONCAT()` | `\|\|` (operador de concatenación) | `CONCAT()` existe en PostgreSQL, pero `\|\|` es lo idiomático |
| `DROP DATABASE` / `USE` al inicio del script | eliminado | En contenedor la base la crea `POSTGRES_DB`; en Kubernetes, Alembic |

**Sin `ON UPDATE CASCADE` en la práctica:** se mantiene declarado (igual que el legacy), pero la API
nunca cambia un `id`, así que no se dispara nunca.

## 3. Reglas de negocio (con el archivo del legacy del que salen)

La columna «dónde se aplica» es la parte importante: **la base es la última línea de defensa** (siempre),
la API repite la validación para poder responder `422` con mensaje, y la UI la muestra.

| # | Regla | Origen (legacy) | Dónde se aplica | Comprobado |
|---|---|---|---|---|
| RN-01 | `nombre_usuario` único, 3–50 caracteres (`[A-Za-z0-9_.]`), email único con formato, rol `admin`/`asistente`, contraseña ≥ 8 caracteres y confirmación igual | `usuarios/create.php`, `usuarios/edit.php` | UNIQUE + CHECK (BD) · API | ✅ prueba negativa |
| RN-02 | Créditos entre 1 y 10; horas entero positivo | `cursos/create.php` | CHECK (BD) · API | ✅ prueba negativa |
| RN-03 | Código de estudiante obligatorio, ≤ 20 caracteres, único | `estudiantes/create.php` | UNIQUE + CHECK (BD) · API | ✅ prueba negativa |
| RN-04 | DNI obligatorio, exactamente 8 dígitos, único | `estudiantes/create.php` | UNIQUE + CHECK (BD) · API | ✅ prueba negativa |
| RN-05 | Email opcional, pero si viene debe tener formato válido | `estudiantes/create.php` | CHECK (BD) · API | ✅ prueba negativa |
| RN-06 | Periodo con formato `AAAA-MM` | `matriculas/create.php` + `edit.php` | CHECK (BD) · API | ✅ prueba negativa (`2026-13`, `2026/02`) |
| RN-07 | Estado de la matrícula: `activa` o `retirado`. Retirar es **baja lógica**, el registro se conserva | `matriculas/edit.php` | CHECK (BD) · API | ✅ prueba negativa |
| RN-08 | Un estudiante no puede repetir el mismo curso en el mismo periodo | `matriculas/create.php` (comentario de cabecera + `UNIQUE KEY uq_matricula`) | UNIQUE (BD) · API (`409`) | ✅ prueba negativa |
| RN-09 | Toda matrícula apunta a un estudiante y a un curso existentes | FK del legacy | FK (BD) | ✅ prueba negativa |
| RN-10 | Borrar un estudiante o un curso arrastra sus matrículas (integridad referencial) | `estudiantes/delete.php`, `cursos/delete.php` (`ON DELETE CASCADE`) | FK ON DELETE CASCADE | ✅ prueba en transacción |
| RN-11 | Nadie puede desactivar su propia cuenta | `usuarios/edit.php` (`No puedes desactivar tu propia cuenta`) | **API** (necesita el usuario de la sesión; la BD no lo puede saber) | ⏳ Sprint 1 |
| RN-12 | Fecha de nacimiento y fecha de matrícula deben ser fechas reales | `checkdate()` en `estudiantes/create.php` y `matriculas/create.php` | tipo `date` de PostgreSQL + API | ✅ implícito |
| RN-13 | Login: el usuario entra con `nombre_usuario` **o** email, y si está inactivo no entra | `login.php` | API | ⏳ Sprint 1 |
| RN-14 | No se registran notas de una matrícula en estado `retirado` (**409**). Retirar una matrícula **no borra** las notas ya registradas | D-06 (no viene del legacy: el legacy no tenía notas) | **Trigger** en `notas` (ERRCODE 23514) + API con el 409 | ✅ prueba negativa (T1.5) |
| RN-15 | **Nota del curso** = media aritmética de sus notas, 2 decimales. **Promedio del periodo** = media ponderada por créditos de los cursos **con** notas; curso sin notas = `null` y no cuenta como 0 | D-03 | API (las dos consultas exactas están verificadas en §7) | ✅ verificado con datos |
| RN-16 | Dato de la nota: `0..20` (2 decimales), `tipo ∈ {practica, parcial, final}`, `numero ≥ 1`, única por `(matrícula, tipo, numero)` | C-24/C-25 del alcance (el legacy no tenía notas) | CHECK + UNIQUE (BD) · API (`422`/`409`) | ✅ 5 pruebas negativas |

**Regla que NO se traduce tal cual (decisión tomada, no olvido):** el legacy hacía `LIKE '%texto%'` en el
buscador y funcionaba sin distinguir mayúsculas ni tildes porque la collation de MySQL lo permitía.
En PostgreSQL eso **no pasa de gratis**: hay que usar `ILIKE` y, para las tildes, `unaccent`. Está medido
en §6.3 — si @dev copia el `LIKE` tal cual, el buscador devuelve 0 resultados y no avisa.

### 4.1 Flujos detallados de los casos que importan

**CU-10 · Registrar matrícula**
- **Actor:** usuario autenticado. **Disparador:** POST del formulario «Nueva matrícula».
- **Entra:** `estudiante_id`, `curso_id`, `periodo` (`AAAA-MM`), `fecha_matricula`, `estado` (default `activa`).
- **Flujo normal:** valida formato de periodo y fecha → verifica que el estudiante y el curso existan y
  estén activos → inserta → responde `201` con la matrícula creada.
- **Alternos:** `422` si el periodo no es `AAAA-MM` o la fecha no es real · `404` si el estudiante o el
  curso no existen · `409` «Ese estudiante ya está matriculado en ese curso para el periodo indicado»
  (era el mensaje exacto del legacy al capturar el `23000`).
- **Datos que salen:** matrícula + nombre del estudiante + curso + créditos.

**CU-11 · Editar / retirar matrícula**
- **Flujo normal:** carga la matrícula, permite cambiar estudiante, curso, periodo, fecha y estado;
  guarda.
- **Alternos:** mismo `409` de RN-08 al cambiar a una combinación ya existente · **retirar** una
  matrícula no la borra: pasa a `estado='retirado'` y sale de los KPIs, pero sigue en el historial
  (importante para el informe académico).
- **Nota de UX (del legacy):** el listado pinta `Activa`/`Retirado` con badges distintos; el dato que
  mueve el KPI es solo `activa`.

**CU-06 / CU-08 · Eliminar estudiante o curso**
- **Flujo normal:** confirma el borrado (el legacy pedía confirmación con el nombre), borra la fila y
  **la base borra sus matrículas por cascada**.
- **Alterno:** el mensaje del legacy lo dice explícito: «Curso eliminado correctamente (sus matrículas
  también, por integridad referencial)». En la API nueva conviene responder `409` con el conteo de
  matrículas afectadas antes de aceptar, en lugar de borrar en silencio (**recomendación**, decisión de @pm).
- **Alternativa no destructiva disponible:** `estado=false` (baja lógica) es lo que el legacy hacía con
  los formularios de edición; la API debería ofrecer las dos cosas (RFC 7231: borrar = `DELETE`).

**CU-02 · Dashboard**
- **Flujo normal:** 4 conteos (`estudiantes activos`, `cursos activos`, `matrículas activas`, `usuarios
  activos`) + agrupado de matrículas activas por curso (top 5) + últimos 6 estudiantes.
- **Verificado con datos reales:** 12 / 7 / 23 / 1 y el agrupado suma 23 (coincide con el KPI, algo que
  el legacy no comprobaba).
- **Alterno:** sin matrículas, los top cursos devuelven lista vacía (no es error).

**CU-14 · Registrar nota**
- **Actor:** admin o asistente. **Disparador:** POST desde la ficha de la matrícula.
- **Entra:** `tipo` (`practica`|`parcial`|`final`), `numero` (≥ 1), `nota` (0..20, 2 decimales), `fecha_registro` (opcional, por defecto hoy), `observacion` (opcional).
- **Flujo normal:** valida el rango y el tipo → comprueba que la matrícula exista y **no** esté `retirado` → inserta → `201`.
- **Alternos:** `422` si `nota=21`/`-1`, `tipo="examen"` o `numero=0` · `409` si repite `(matrícula, tipo, número)` · `409` **«no se califica a una matrícula retirada»** (RN-14).

**CU-15 · Boleta del periodo**
- **Flujo normal:** por cada matrícula del estudiante en el periodo: sus notas, la **nota del curso** (media aritmética, 2 decimales) y, al final, el **promedio del periodo** ponderado por créditos.
- **Alterno:** un curso **sin notas** sale con `nota: null` y **no** cuenta como 0 en el promedio (C-28).
- **Verificado con números:** notas 14/16/18 en C101 (4 créditos) y 11 en C102 (3 créditos) → nota del curso **16.00** y **11.00**; promedio del periodo **13.86** (ponderado: `(16×4 + 11×3) / 7`), que **no** es el promedio simple **13.50** — las dos cifras están fijadas como comprobación, para que nadie confunda los dos criterios.

## 6. Hallazgos (encontrados probando, no leyendo)

### 6.1 El hash bcrypt del seed: funcional, pero no verificable con pgcrypto
El seed del legacy trae `$2y$10$Tzgm...` para `Admin123!`. Verificado **funciona** con
`bcrypt==4.2.1` de PyPI (`checkpw(b'Admin123!', hash) → True`, evidencia en
`hash-legacy-python-bcrypt.txt`), que es lo que usará la API — así que el hash **se deja tal cual**, no
se regenera (conserva la trazabilidad con el legacy).
Pero **pgcrypto no sirve para comprobarlo**: acepta la cadena `$2y$` y calcula un digest distinto
(`verifica_2y = f`), solo coincide si se normaliza el prefijo a `$2a$` (`verifica_2a = t`). Con `$2b$`
tampoco. Probé además 10 contraseñas candidatas con pgcrypto: solo `Admin123!` (normalizando a `$2a$`)
coincide → la contraseña documentada por el legacy es la correcta.
**Para @dev:** usá `bcrypt` (o `passlib`) y verificá el `$2y$` tal cual; no hace falta migrar el hash ni
resembrar la contraseña.

### 6.2 Los ids no son consecutivos (y está bien)
`nextval` **no se revierte** con un ROLLBACK, y un INSERT rechazado por un CHECK **también consume** el
siguiente id. Comprobado: tras 3 INSERT fallidos de curso, el siguiente id válido fue 11 en lugar de 8.
No es un bug — es cómo funciona IDENTITY — pero hay que saberlo antes de que alguien "arregle" la
secuencia a mano. En el seed se resuelve con `setval` al final, que se sincroniza con `max(id)`.

### 6.3 El buscador del legacy no se puede copiar literal (LIKE → ILIKE + unaccent)
Medido con 100.000 estudiantes (`busqueda-rendimiento.txt`):

| Consulta | Resultado |
|---|---|
| `LIKE '%quispe%'` (como el legacy) | **0 filas** |
| `ILIKE '%quispe%'` | 2 filas (las del legacy) |
| `ILIKE '%huaman%'` sin `unaccent` | **0 filas** (el dato es `Huamán`) |
| `unaccent(apellidos) ILIKE unaccent('%huaman%')` | 2 filas |
| `EXPLAIN ANALYZE` del buscador con `ILIKE` sobre 100.000 filas | `Seq Scan` → **112 ms** |
| Lo mismo con índice GIN trigram sobre `lower(apellidos \|\| ' ' \|\| nombres)` | `Bitmap Index Scan` → **0,09 ms** |
| Intentar indexar `unaccent(...)` directamente | `ERROR: functions in index expression must be marked IMMUTABLE` |

**Recomendación para @dev:** el buscador va con `ILIKE` **+ `unaccent`** — no es opcional: el criterio
`C-08` exige la misma cantidad de filas con `huaman`, `Huamán` y `HUAMAN`, y con `ILIKE` solo son 0 / 1 / 0
(BUG-07 de @qa, medido y fijado como comprobación). La extensión ya se crea en `01-schema.sql`
(`CREATE EXTENSION IF NOT EXISTS unaccent;`) y **debe ir también en la revisión inicial de Alembic** (D-14).
El índice trigram sigue siendo un "si algún día la tabla crece": necesita una función `IMMUTABLE` propia
que envuelva a `unaccent` (el error de arriba es exactamente eso). Con 12 estudiantes no hace falta; está
medido para que la decisión sea con números, no con opiniones.

### 6.4 La cascada funciona, y conviene no usar `DELETE` a ciegas
Verificado: borrar el curso 5 eliminó sus 3 matrículas; borrar el estudiante 2, sus 2 matrículas.
Funciona, pero es silencioso. Sugerencia para la API: `409` con el conteo de matrículas afectadas
(decisión de @pm, ver §4.1).

## 7. Tabla `notas` (entregada en el Sprint 1 — T1.5, decisión D-01)

El sistema legacy se llama «Sistema Administrativo Web» y **no tiene notas**, aunque el nombre del
proyecto del curso es «Matrículas **y Notas**». @pm cerró D-01: las notas **sí** entran, en el Sprint 3 y
como esquema **aditivo** (`db/init/04-notas.sql` + `v_notas_detalle` + RN-14/15/16), sin tocar ninguna de
las 4 tablas del legacy. Entregado y verificado: `db/verificacion/verificar_notas.sql` → **32 OK**
(evidencia: `docs/analisis/evidencia/verificacion-notas.txt`).

```sql
CREATE TABLE notas (
    id             integer     GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    matricula_id   integer     NOT NULL,
    tipo           varchar(15) NOT NULL,            -- practica | parcial | final
    numero         smallint    NOT NULL DEFAULT 1,  -- 1..N dentro del tipo
    nota           numeric(4,2) NOT NULL,           -- 0.00 .. 20.00
    fecha_registro date        NOT NULL DEFAULT CURRENT_DATE,
    observacion    varchar(200) NULL,
    creado_en      timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT fk_notas_matricula FOREIGN KEY (matricula_id) REFERENCES matriculas (id) ON DELETE CASCADE,
    CONSTRAINT uq_notas_matricula_tipo_numero UNIQUE (matricula_id, tipo, numero),
    CONSTRAINT ck_notas_tipo   CHECK (tipo IN ('practica','parcial','final')),
    CONSTRAINT ck_notas_nota   CHECK (nota >= 0 AND nota <= 20),
    CONSTRAINT ck_notas_numero CHECK (numero >= 1)
);
```

Decisiones de diseño de la tabla (todas verificadas, ninguna al azar):

| Punto | Por qué |
|---|---|
| La nota cuelga de la **matrícula**, no del estudiante | Es la única forma de que un retiro no borre el historial y de que borrar al estudiante arrastre sus notas (C-29) |
| `numeric(4,2)` | Guarda hasta 20.00 y redondea a 2 decimales lo que llegue con más (`16.005 → 16.01`, fijado como comprobación para que no sorprenda a nadie) |
| `UNIQUE (matrícula, tipo, número)` | Impide cargar dos veces la misma práctica; la API responde `409` |
| RN-14 con **trigger** (no solo en la API) | «No se califica a una matrícula retirada» es un dato, no una regla de sesión: se aplica en la base (`ERRCODE 23514`) y la API responde `409` antes. El trigger es **solo de INSERT**: corregir una nota ya registrada de una matrícula que después se retiró sigue permitido. Si @dev prefiere validarlo solo en la app, se quita borrando el trigger (una línea) |
| `v_notas_detalle` | La nota con matrícula, estudiante, curso, créditos y periodo: es la base de la boleta (C-28) |

**RN-15 (los dos cálculos), las consultas exactas ya verificadas** — la media del curso se guarda por
curso y el promedio del periodo solo suma los cursos **con** notas:

```sql
-- Nota del curso (media aritmética, 2 decimales)
SELECT round(avg(n.nota), 2) FROM notas n WHERE n.matricula_id = $1;          -- 16.00

-- Boleta del periodo (C-28): un curso sin notas sale con `nota` NULL
SELECT m.id AS matricula_id, c.codigo, c.nombre, round(avg(n.nota), 2) AS nota_curso
FROM matriculas m
JOIN cursos c     ON c.id = m.curso_id
LEFT JOIN notas n ON n.matricula_id = m.id
WHERE m.estudiante_id = $1 AND m.periodo = $2
GROUP BY m.id, c.codigo, c.nombre;                                            -- 3 filas, una con NULL

-- Promedio del periodo: media ponderada por créditos de los cursos con notas
SELECT round(sum(nota_curso * creditos) / sum(creditos), 2) FROM (
    SELECT m.id, c.creditos, round(avg(n.nota), 2) AS nota_curso
    FROM matriculas m
    JOIN cursos c ON c.id = m.curso_id
    JOIN notas n  ON n.matricula_id = m.id
    WHERE m.estudiante_id = $1 AND m.periodo = $2
    GROUP BY m.id, c.creditos) s;                                             -- 13.86
```

Comprobado con datos: notas 14/16/18 en C101 (4 créditos) y 11 en C102 (3 créditos) → notas de curso
**16.00** y **11.00**, promedio del periodo **13.86**; el promedio **simple** daría 13.50 y también está
fijado como comprobación, para que quede claro que se está usando el ponderado (D-03).
